# 知识工作台 · DSH 插件

DeepSeek Harness 的本地知识工作台插件。它把「研究 → 审阅 → 入库」做成一个常驻循环：agent 查资料、写候选卡片，你在侧栏工作台或 Obsidian Bases 数据库里确认，确认后的卡片成为正式笔记。所有内容是本机 Markdown，可以直接用 Obsidian 打开。

这个仓库是原「悟 · 个人知识工作台」原型在 DSH 上的插件化版本：原型里的本地仓库、候选卡审阅、每日研究、后续问题与偏好，分别落到了 DSH 的 Markdown 仓库、槽位页面、`schedule` 服务和工具注册表里。仓库现在生成 Obsidian Bases `.base` 文件，把候选卡、正式笔记和研究简报变成可筛选、分组、排序的数据库视图。

## 位置

- **面板**：左侧面板图标列表里的书本图标「知识工作台」，与「插件」「定时任务」同一列。
- **数据库**：仓库根目录的 `知识工作台.base`，用 Obsidian 1.9+ 的 Bases 打开，含待审阅、收件箱、知识库（卡片/表格）、研究简报和全部笔记视图。
- **工具**：`knowledge_status`、`knowledge_capture`、`knowledge_search`、`knowledge_read`、`knowledge_ask`、`knowledge_brief`。
- **排程**：在「知识工作台 → 研究记录」开启每日研究，任务由 DSH 的 `schedule` 服务托管，运行在一个普通新会话里；研究视图里可以改时间，也可以编辑每轮交给 agent 的研究指令（留空或「恢复内置」跟随插件更新）。

## 安装

用 DSH 的 **Plugins → 添加插件 → 本地目录**，选择这个仓库根目录；或在本机已安装时用：

```powershell
# 在 DSH 的 Creator/管理会话里，让 agent 执行 install_bundle
# target = 本仓库根目录的绝对路径
```

安装后插件行是 `@local/dsh-knowledge-workbench`，Host 半与浏览器半同时生效。

## 界面

整页是一屏分栏，不做整页滚动：

- **顶栏**：面板名与一句上下文（日期、待审阅/暂缓/已入库的数量），右侧是研究状态（点一下跳到研究视图）、刷新和「立即研究」。研究排队后会显示「研究已排队」，跑完自动消失。
- **标签**：收件箱 / 知识库 / 研究 / 偏好与问题，下划线样式，后面的数字是各自待处理的数量。
- **收件箱**：左侧列表逐条展示标题、摘要、日期与标签；每行右侧可直接「确认入库 / 暂缓 / 跳过」，不用先打开卡片，也不会把正在阅读的卡片切走。右侧阅读区单独滚动，确认当前卡片后自动跳到下一张待审阅卡片。
- **知识库 / 研究**：同样的左列表右阅读。知识库为空时会说明怎么用 Obsidian 打开 `知识工作台.base`；研究视图左侧是每日研究（开关、时间、研究指令、下次/上次运行）与简报列表，右侧是选中的简报。
- **偏好与问题**：左栏编辑偏好（兴趣会显示成可删除的标签），右栏管理排队问题；未保存时标题旁有提示。
- **底栏**：仓库与 `知识工作台.base` 的路径（可复制），以及当前视图的快捷键提示。

键盘：`j` / `k` 在列表中移动并打开，`a` 确认、`h` 暂缓、`s` 跳过（作用于当前焦点行或已打开的卡片），`/` 搜索，`Esc` 清除搜索或取消删除。窄屏（≤840px）下列表与阅读区切换为单栏，阅读区左上角有返回按钮。所有颜色、字号和边框都来自 DSH 主题 token，跟随浅色/深色主题；标题、简介与下划线标签也按 DSH 插件页的字号与 44px 标签条对齐。

## 循环

1. 「立即研究」或每日定时 → DSH 新建普通会话，读取兴趣、基础、目标、阅读偏好、队列和近期研究主题。先发散出 2–3 个待检验的问题，再用 `knowledge_search` 查重；命中相关卡片后用 `knowledge_read` 读正文，确认实际知识缺口。
2. 用 `web_search` / `web_fetch` 阅读原始资料、双方论述和反例，再决定最终研究问题。允许推翻最初假设。默认每轮只完成一篇概念解释或概念比较，先写草稿，再单独审读修订，通过后调用 `knowledge_capture` 写入 `inbox/`。证据不足或没有知识增量时允许零产出，仍写当天 `briefs/` 说明原因。知识库不收操作手册、版本变更日志、函数签名和新闻。
3. 你在「知识工作台 → 收件箱」读卡片，或直接打开 Obsidian Bases 的 `知识工作台.base`：确认入库、暂缓、跳过、恢复待审阅、删除，或「继续深挖」把问题加入队列。
4. 确认后卡片移动到 `library/`；删除只移走候选，不影响已入库笔记。

研究指令要求保存前查重并阅读相近内容；工具额外拒绝规范化后同名的卡片。程序并不具备语义查重能力，换词重复仍需研究与审阅识别。工具也不能修改已有笔记：没有实质增量就跳过，有新增定义、机制、区别或边界才另写明确的新问题。简报中的「接着探索」只保留值得继续研究的概念层问题。

研究指令可在「研究 → 研究指令」编辑；正文留空表示使用内置版本。每日任务保存了自己的指令副本：更新插件后，如果显示「同步研究指令」，点击即可更新已有任务，保留时间、开关和任务身份；重新开启每日研究也会使用当前指令。自定义正文不会被新版内置指令覆盖，若希望采用新版流程，请点「恢复内置」。保存指令时若每日任务更新失败，页面会报告错误并保留同步入口，便于重试。

只有你能确认入库；agent 没有发布工具。

## 卡片格式

每张卡围绕一个问题形成完整解释。新研究使用 `concept`（概念解释）或 `comparison`（概念比较），不强制写步骤、代码、类比、案例或「30 秒验证」。正文通常约 800–1600 汉字，按问题复杂度调整，准确和可读优先于篇幅。

| 字段 / 正文章节 | 内容要求 |
| --- | --- |
| `title` | 点明概念、研究问题或关键区别，保留条件，允许解释型或问题型标题 |
| `takeaway` / `summary` | 一两句新认识，供列表和 Bases 显示，不强迫写行动口号 |
| `question` / 研究问题 | 读完需要消除的具体困惑 |
| `definition` / 概念定义 | 准确定义与必要术语；比较题分别定义双方并说明为何容易混淆 |
| `mechanism` / 机制解释 | 用连贯段落解释过程、关系与因果链，标明推测，不压成一句话 |
| `subjects`、`comparison` / 概念比较 | 比较题专用：恰好两个对象，2–6 个不重复的共同维度，每行包含双方解释和差异影响 |
| `limits` / 边界与取舍 | 前提、反例、代价、误用；比较题另说明重叠关系和选择条件 |
| `evidenceNote` / 证据与不确定性 | 区分原文陈述、作者观点与研究者推论，保留争议和未知 |
| `reviewNote` / 审读记录 | 草稿完成后，记录审读发现的问题、具体修订和剩余疑点；明确这是作者自检 |
| `related` / 关联（可选） | 相关卡片链接及关系；卡片保留与标题同名的 `aliases` |
| `sources` / 来源 | 1–5 条不同原文，必填标题、URL、逐字短引文和所支撑的具体论断；比较题至少两条，研究时需确认覆盖双方 |

程序检查字段、长度、URL 格式、来源重复和比较结构，超长新卡会被拒绝而非静默截断。**程序不会联网核对引文，也不能判定论断真假或两条来源是否独立。** 阅读原文、核对支持关系、查反例和编辑审读由研究会话完成；事实质量仍需用户审阅。来源数量不能替代证据质量。

阅读区增大正文间距，比较表可独立横向滚动；来源和审读记录默认折叠，证据限制保持在正文中。重复的文档标题会从阅读区去掉，Markdown 文件仍保留标题。

旧版「场景 / 原理 / 做法 / 怎么验证」以及更早的「核心结论 / 为什么 / 怎么用」卡片继续支持读取、检索、审阅和入库，不批量改写。存储接口保留旧输入兼容，agent 当前工具声明只提供新结构。入库仍会去掉候选卡底部的审阅操作提示。

## Obsidian Bases 数据库

插件在 `<vault>/知识工作台.base` 生成一个 Obsidian Bases 文件，把笔记属性当作列：

| 视图 | 内容 |
| --- | --- |
| 待审阅 | `inbox/` 里 `review == "待审阅"` 的卡片，按创建日倒序，带一句话、标签和来源数 |
| 收件箱（全部） | 所有候选卡，按 `review` 分组（待审阅 / 暂缓 / 跳过 / 确认） |
| 知识库 | `library/` 的卡片视图 |
| 知识库（表格） | `library/` 的表格，带来源链接 |
| 研究简报 | `briefs/` 的每日简报，带今日重点和问题数 |
| 全部笔记 | 最近修改的 Markdown 文件，便于直接跳到源文件 |

卡片上的数据库属性由 `knowledge_capture` 写入：

- `title`、`aliases`、`summary`（一句话「所以呢」）、`review`、`created`、`approved`、`tags`
- `source_count`（数字）和 `sources`（URL 列表）
- 新卡另有 `card_type`（`concept` / `comparison`）和 `question`，可在 Bases 中添加为列

`.base` 文件只在缺失时生成。**你在 Obsidian 里改过的视图、列、筛选和排序不会被插件覆盖**；删掉该文件后，下一次刷新工作台会重新生成默认版本。

## 审阅的权威来源

候选卡片就是普通 Markdown，两种确认方式等价：

1. 在侧栏「知识工作台」点「确认入库」；
2. 在 Obsidian Bases 表格（或笔记属性）里把 `review` 改成 `确认`。工作台每 15 秒刷新、手动刷新或下次 `knowledge_status` 时会扫描并发布。

确认时把**当前文件内容**移动到 `library/`，所以确认前在 Obsidian 里的编辑会一起入库。扫描只接受 frontmatter `id` 与文件名一致的候选卡，且目标已存在时不会覆盖。

## 仓库结构

```
<vault>/
  知识工作台.base   Obsidian Bases 数据库（视图、筛选、列、排序）
  inbox/           候选卡片（frontmatter 带 review: 待审阅）
  library/         确认后的正式笔记
  briefs/          每天一份研究简报
  偏好.md          兴趣 / 基础 / 目标 / 阅读习惯的镜像
  待研究.md        后续问题镜像；追加 `- 问题` 也会进队列
  .workbench/      状态、回收站、临时写入
```

默认 vault 是 `~/Documents/DSH知识库`。可以在 profile 的 `cordis.patch.yml` 里给这一行加 `config.vault` 改到别处，例如指向已有的 Obsidian 仓库：

```yaml
- id: knowledge-workbench
  name: '@local/dsh-knowledge-workbench'
  config:
    vault: 'D:\Notes\悟'
```

`config.timeZone` 可覆盖日期所用时区（默认取本机时区）。

## 实现

| 文件 | 职责 |
| --- | --- |
| `index.js` | Host 半：vault 配置、浏览器 JSON API、`schedule` 排程、工具注册 |
| `lib/store.js` | Markdown 仓库：候选卡、审阅迁移、偏好与问题镜像、简报、检索 |
| `lib/tools.js` | 六个 agent 工具（原始 JSON Schema，不依赖 DSH 内部包） |
| `lib/note.js` | frontmatter 读写、卡片渲染、日期与 note id |
| `lib/article.js` | 新卡结构与长度校验、共同比较维度、来源论断映射检查；不执行事实核验 |
| `lib/bases.js` | Obsidian Bases 文件内容与属性确认常量 |
| `lib/research.js` | 每日/立即研究的提示词（正文可在面板编辑）、默认指令与时间校验 |
| `client.js` | 浏览器半：侧栏入口 + 知识工作台整页（分栏布局、快捷键、只读主题 token） |
| `locale/` | 中英文插件标题与详情 |
| `docs/` | 插件详情页配图 |

浏览器半只调用 Host 注册的 `/plugin/dsh-knowledge-workbench` 路由；该路由校验 Host 与浏览器会话（`ctx.connection.requestRejection`），只服务本机页面。

## 验证

```powershell
node --test
```

测试覆盖概念解释和比较卡的保存、证据映射、比较维度、超长拒绝及完整保留、旧格式兼容、检索、人工与 Bases 确认入库、去掉 review 提示、Bases 种子不覆盖编辑、偏好与问题镜像、简报、同名去重、六个工具链路、浏览器 API 鉴权，以及每日研究指令同步与失败重试。浏览器测试还执行实际 Markdown 渲染函数，检查折叠区、横向表格、转义分隔符、标题去重和代码块；同时检查主题 token、中英文字典及键盘操作约定。

程序测试不能证明生成文章的质量。升级后应以同一组研究问题对照旧版，人工检查：能否准确复述定义、机制是否解释原因、比较是否公平且使用共同维度、主要论断是否有匹配原文、是否保留边界和不确定性、删去口号后是否仍有知识。出现无依据数字、错引或用类比替代定义，应修订或跳过，不以字数或卡片数量作为合格标准。

UI 渲染需要在 DSH 页面里人工确认；Host 半的安装状态、工具注册、槽位注册与接口鉴权可通过 DSH 的运行时检查验证。
